# Phase 2 test checklist — mTLS relay

Run these from **your own machine** (not the EC2 box) so you're testing the
same public path Vercel will eventually use: `13.63.60.102:8443` over the
open internet. You'll need `openssl` and, for test 5, a `mysql` client —
both are already on most laptops; Git Bash on Windows ships openssl.

Copy `client.crt`, `client.key`, and `ca.crt` from `infra/mtls-relay/certs/`
(generated by `01-generate-ca-and-certs.sh`) to wherever you're running
these commands.

---

## Test 1 — stunnel is running on EC2

Run on the EC2 instance (via Instance Connect):

```bash
sudo systemctl status stunnel --no-pager
sudo ss -tlnp | grep 8443
```

Expect: `active (running)` and a listener on `0.0.0.0:8443`.

## Test 2 — EC2 → RDS still works privately

Run on the EC2 instance:

```bash
timeout 3 bash -c '</dev/tcp/172.31.29.62/3306' && echo "RESULT=SUCCESS" || echo "RESULT=FAIL"
```

Expect: `RESULT=SUCCESS` (this is the same private-VPC check from Phase 1 —
confirms nothing about the stunnel install broke the underlying path).

## Test 3 — connect WITHOUT a client cert → must fail

From your own machine:

```bash
echo | openssl s_client -connect 13.63.60.102:8443 -CAfile ca.crt
```

Expect: a TLS handshake failure (e.g. `alert handshake failure` or
`sslv3 alert certificate required`), no MySQL data returned. This is
required to pass — if it succeeds, `verify = 2` isn't taking effect and
must be fixed before continuing.

## Test 4 — connect WITH the valid client cert → must succeed

```bash
echo | openssl s_client -connect 13.63.60.102:8443 \
  -cert client.crt -key client.key -CAfile ca.crt
```

Expect: `Verify return code: 0 (ok)` near the bottom of the output, and no
handshake alert.

## Test 5 — authenticated connection is actually forwarded to RDS

Because stunnel just relays raw bytes to MySQL after the TLS handshake, a
successful connection should show the MySQL server's initial handshake
packet (binary, but recognizably starts with a protocol-version byte and
often contains the string `mysql_native_password` or a version string like
`8.0.` / `10.x.` for MariaDB):

```bash
openssl s_client -connect 13.63.60.102:8443 \
  -cert client.crt -key client.key -CAfile ca.crt -quiet 2>/dev/null | head -c 200 | xxd
```

Expect: readable bytes containing a MySQL/MariaDB version string — proof
the bytes are coming from RDS, not stunnel itself.

For a cleaner end-to-end check, use `mysql` client with `--ssl` disabled
inside the mTLS tunnel (stunnel is doing the TLS layer, so the inner MySQL
connection itself should be plain):

```bash
mysql -h 127.0.0.1 -P 3307 -u <db_user> -p --ssl-mode=DISABLED &
# in another terminal, run a local stunnel client that forwards
# localhost:3307 -> 13.63.60.102:8443 with the client cert, then connect
# above. (A minimal local client.conf for testing:)
cat > client-test.conf <<'EOF'
client = yes
[kwanomzi-db-relay-test]
accept = 127.0.0.1:3307
connect = 13.63.60.102:8443
cert = client.crt
key = client.key
CAfile = ca.crt
verifyChain = yes
EOF
stunnel client-test.conf
```

Expect: `mysql` connects and you can run `SELECT 1;`. This is the strongest
proof of end-to-end forwarding — do this one if `mysql` and local `stunnel`
are available; otherwise Test 5's `xxd` check is sufficient evidence.

## Test 6 — consistent success, not a fluke

```bash
for i in $(seq 1 10); do
  echo -n "attempt $i: "
  echo | openssl s_client -connect 13.63.60.102:8443 \
    -cert client.crt -key client.key -CAfile ca.crt 2>&1 \
    | grep -q "Verify return code: 0" && echo OK || echo FAIL
done
```

Expect: `OK` all 10 times.

## Test 7 — unauthorized clients cannot reach MySQL through the relay

Same as Test 3, but also confirm with a plain TCP tool that no MySQL data
leaks before the TLS handshake completes:

```bash
(echo -n ""; sleep 1) | timeout 3 openssl s_client -connect 13.63.60.102:8443 2>&1 | tail -20
```

Expect: handshake failure only — no MySQL greeting bytes anywhere in the
output, confirming stunnel never forwards to RDS until mTLS succeeds.
